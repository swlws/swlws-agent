## 2. 需求理解

本需求旨在**提升用户对可用 Skill 和 MCP Server 的可发现性**，通过**在输入框输入 `/` 时展示浮层、支持搜索过滤和键盘导航快速选择**实现能力感知与调用入口，不包含明确的排除范围（搜索、键盘导航、嵌套子菜单均在做）。

与现有功能的关系：修改 `src/fe/pages/Chat/InputBar.tsx`，修改 `src/fe/pages/Chat/SlashMenu.tsx`，不涉及后端改动。

## 5. 技术方案设计

### 5.1 浮层触发条件与搜索关键词提取

**问题**：如何同时支持「输入 / 触发浮层」和「/ 后继续输入过滤」

**方案 A**：value 派生（无独立 showMenu state）
- `showMenu = value.startsWith("/")`
- `query = value.slice(1)`
- 优点：逻辑简单，状态最少
- 缺点：Esc 关闭浮层必须清空 value；用户若先输入其他内容再输入 / 不触发（符合 PRD 当前描述）

**方案 B**：独立 showMenu state
- 引入 `showMenu: boolean`，`onChange` 时判断是否展示，Esc 只 `setShowMenu(false)`
- 优点：Esc 可保留输入内容，交互更细腻
- 缺点：状态多一个，需同步管理

**结论**：采用方案 A，原因：PRD 描述「Esc 关闭，输入框内容不变」在当前 value 只有 `/xxx` 的场景下清空即可；若后续需支持行中触发再升级为方案 B。

---

### 5.2 键盘导航的列表索引管理

**问题**：过滤后列表长度动态变化，activeIndex 需要被约束

**方案**：
- `activeIndex` 存在 `InputBar` state，初始值 `-1`（无高亮）
- 每次 `query` 变化时重置 `activeIndex = -1`
- ArrowDown：`Math.min(activeIndex + 1, filteredList.length - 1)`
- ArrowUp：`Math.max(activeIndex - 1, -1)`（-1 表示无高亮，焦点回到搜索输入）
- Enter：`activeIndex >= 0` 时选中，否则不触发

**结论**：统一管理，filteredList 的计算在 SlashMenu 内部完成，通过 `onActiveChange` 回传父级。

---

### 5.3 搜索匹配策略

对 MCP Server 按 `name` 匹配，对 Skill 按 `name` 和 `displayName` 匹配，均使用 `toLowerCase().includes(query.toLowerCase())`，无需引入模糊搜索库。
