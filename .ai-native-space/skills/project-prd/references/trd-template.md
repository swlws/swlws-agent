# TRD 模板与填写规范

> TRD（Technical Requirements Document）由 project-prd skill 自动生成，基于 PRD 评审通过后的内容填写。

---

## TRD 文件头

```markdown
# TRD：<需求名称>

> 来源 PRD：`<PRD 文件路径>`
> 生成时间：<YYYY-MM-DD HH:mm>
> 评审结论：通过 / 含问题（见第 1 节）
```

---

## 第 1 节：评审摘要

仅当评审存在问题（完整性缺失或高/中风险）且用户选择「忽略问题直接生成」时填写：

```markdown
## 1. 评审摘要

> ⚠️ 以下问题在生成 TRD 时被忽略，开发过程中需特别注意。

### 完整性问题
- [C-X] 描述

### 技术风险
- 🔴 [R-X] 描述
- 🟡 [R-X] 描述
```

无问题时：`> ✅ PRD 评审通过，无遗留问题。`

---

## 第 2 节：需求理解

用一段话重述 PRD 的核心目标，确认理解对齐。格式：

```markdown
## 2. 需求理解

本需求旨在 **[核心目标]**，通过 **[关键手段]** 实现 **[预期效果]**，
不包含 **[排除范围]**。

与现有功能的关系：[新增 / 修改 / 替换] `[模块/功能名]`。
```

---

## 第 3 节：工程任务拆解

将 PRD 功能拆解为具体工程任务，细化到文件/接口/类型。格式：

```markdown
## 3. 工程任务拆解

### T-1：<任务名>
- **类型**：新建 / 修改 / 删除
- **涉及文件**：
  - `src/be/engine/runners/<name>/index.ts` — 实现 ModeRunner 接口
  - `src/be/engine/runners/index.ts` — 注册到 modeRunners Map
- **接口变更**：（如无则填「无」）
  - 新增：`POST /api/<path>` → `{ field: type }`
- **依赖任务**：T-X（需先完成）

### T-2：<任务名>
...
```

**任务拆解原则**：
- 每个任务对应单一职责（单个文件或接口），可独立完成和审查
- 涉及前后端同步的任务（如新增 CardType），拆为独立的前端任务和后端任务
- 新增配置字段拆为：类型定义、默认值、UI 控件三个子任务

---

## 第 4 节：现有模块影响分析

对照工程架构，标出本需求改动涉及的所有现有模块。格式：

```markdown
## 4. 现有模块影响分析

| 模块 / 文件 | 影响类型 | 影响描述 |
|------------|---------|---------|
| `src/be/engine/intent/resolver.ts` | 修改 | 需在路由矩阵中插入新 Runner 优先级规则 |
| `src/fe/lib/chatSseClient.ts` | 修改 | 新增 CardType 枚举值 |
| `src/fe/pages/Chat/MessageItem.tsx` | 修改 | 新增对应渲染分支 |
| `src/be/config/settings.ts` | 修改 | 新增 AppSettings 字段和默认值 |
| （无影响的模块不列出） | | |
```

---

## 第 5 节：技术方案设计

描述关键技术决策，含方案选型和理由。格式：

```markdown
## 5. 技术方案设计

### 5.1 <关键决策点 1>

**问题**：<需要做什么决策>

**方案 A**：<描述>
- 优点：
- 缺点：

**方案 B**：<描述>
- 优点：
- 缺点：

**结论**：采用方案 A，原因：<简要说明>

---

### 5.2 <关键决策点 2>
...
```

**何时需要写技术方案**：
- 有多种实现路径可选时
- 涉及性能/并发/一致性权衡时
- 需要新引入外部依赖时
- PRD 未明确技术实现方向时

---

## 第 6 节：工作量评估

| 任务 ID | 任务名 | 规模 | 工作量说明 |
|---------|-------|------|-----------|
| T-1 | 新增 XXRunner | M | 参考已有 re-act runner 实现，主要是逻辑适配，约 0.5 天 |
| T-2 | 注册 AgentMode | S | 类型定义 + 三处同步，约 1 小时 |
| T-3 | 前端新增 CardType | S | 两处 enum + 一处 switch，约 1 小时 |

**规模定义**：

| 规模 | 参考 |
|------|------|
| XS | < 1 小时，10 行内改动 |
| S | 1-4 小时，单文件或少量联动改动 |
| M | 0.5-1 天，多文件联动，逻辑较复杂 |
| L | 1-3 天，跨层改动，含前后端联调 |
| XL | > 3 天，架构级改动或高不确定性 |

## 第 7 节：风险与注意事项

直接引用 Phase 2 风险评估中命中的条目，补充应对措施：

```markdown
## 7. 风险与注意事项

| 风险 ID | 等级 | 描述 | 应对措施 |
|---------|------|------|---------|
| R-1 | 🔴 | 新增 Runner 影响意图路由优先级 | 修改 resolver.ts 后，逐一验证现有意图路由结果不变 |
| R-9 | 🔴 | CardType 前后端不同步 | T-3 前后端任务设为依赖，同步提交，代码审查时核对两处 enum 值 |
```

## 第 8 节：验收核对表

可执行的 checklist，供开发自测和代码审查使用：

```markdown
## 8. 验收核对表

### 功能验收
- [ ] 正向 case：[输入描述] → [预期输出]
- [ ] 异常 case：[异常场景] → [预期降级/错误提示]
- [ ] 边界 case：[边界条件] → [预期行为]

### 工程规范自检（引用 project-code-review 清单）
- [ ] 新增 API Route 含 `export const runtime = "nodejs"`
- [ ] 文件写操作使用 `lockedWrite`
- [ ] 新增 CardType 前后端两处 enum 同步
- [ ] 新增 AgentMode 三处 VALID_MODES 同步

### 联调验收
- [ ] [具体联调场景]
```
