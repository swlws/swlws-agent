# project-prd：PRD 完整性检查 → 完善输出

读取草稿 PRD，逐项检查完整性，对「必须」级缺失项追加追问到 PRD 文件尾部，引导用户补充后重跑，直到所有必须项齐全，输出一份完善后的 PRD 文件。

## 主流程

```
Phase 0 读取 PRD    → 解析草稿 PRD，识别文档结构
Phase 1 完整性检查  → 按 [references/completeness.md](references/completeness.md) 逐项核对
Phase 2 评审结论    → 汇总缺失项，AskQuestion 决策
Phase 3 追问补充    → 将「必须」级缺失项以追问格式写入 PRD 尾部，等用户填写后重跑
Phase 4 输出完善 PRD → 所有必须项通过后，整理输出完善版 PRD 到 .ai-native-tmp/prd/<文件名>-final.md
Phase 5 自我进化    → 发现未覆盖的新模式，询问用户后更新规则
```

## Phase 0 — 读取 PRD

1. 用户提供 PRD 文件路径，使用 Read 工具读取完整内容
2. 识别文档包含的结构章节：需求背景与范围 / 功能说明 / 技术指标与接口 / 验收标准
3. 若文件尾部已有 `<!-- 评审反馈 -->` 区块，识别其中的占位符是否已被用户填写

---

## Phase 1 — 完整性检查

按 [references/completeness.md](references/completeness.md) 逐项核对，输出格式：

```markdown
## 完整性检查结果

✅ 通过（N 项）
❌ 缺失/不合格（N 项）：

- [C-1] 必须：需求背景章节缺少「不做什么」边界说明
- [C-6] 必须：功能说明中无任何异常/边界路径描述
```

**通过标准**：❌ 项为 0，或全部为「建议」级（非「必须」级）。

---

## Phase 2 — 评审结论与决策

汇总 Phase 1 结果，**必须用 AskUserQuestion** 询问：

**所有必须项通过时**：

| 选项          | 行为         |
| ------------- | ------------ |
| 输出完善版 PRD | 进入 Phase 4 |
| 取消          | 零副作用结束 |

**有「必须」级缺失项时**：

| 选项                     | 行为                                                       |
| ------------------------ | ---------------------------------------------------------- |
| 追加问题到 PRD，等待补充 | 进入 Phase 3，将缺失项写入 PRD 尾部，结束等用户填写后重跑 |
| 取消                     | 零副作用结束                                               |

---

## Phase 3 — 追问补充

使用 Edit 工具在 PRD 文件末尾追加以下格式的内容：

```markdown
---

<!-- 评审反馈：以下问题需补充，填写完成后重新运行 /project-prd -->

**[C-1] 需求背景**
请补充：为什么需要这个功能？（背景/痛点/目标）

> （在此填写）

**[C-3] 排除范围**
请补充：明确不做什么？（防止范围蔓延）

> （在此填写）
```

**规则**：
- 仅追加「必须」级缺失项，「建议」级不追加
- 若 PRD 尾部已有 `<!-- 评审反馈 -->` 区块，**替换整个区块**而非重复追加（更新为当前仍未填写的项）
- 每项格式：`**[C-X] 标题**` + 一句提示语 + `> （在此填写）` 占位符
- 追加完成后告知用户：「已将 N 个问题写入 PRD 文件，请补充后重新运行 /project-prd」

---

## Phase 4 — 输出完善版 PRD

所有「必须」级检查项通过后，将原始 PRD 内容整理为结构化完善版：

1. **移除** `<!-- 评审反馈 -->` 追问区块
2. **整合**用户在追问区块中填写的答案到对应章节（背景并入需求背景、排除范围并入功能说明等）
3. **补全** PRD 标准章节结构（若原文缺少某章节标题，按内容归类补充）
4. 写入路径：`.ai-native-tmp/prd/<原文件名>-final.md`
5. 文件头写入时间戳：`> 完善时间：<YYYY-MM-DD HH:mm>`
6. 告知用户可以运行 `/project-trd <路径>` 生成 TRD

**完善版 PRD 结构**：

```markdown
# <需求名称>

> 完善时间：YYYY-MM-DD HH:mm
> 来源草稿：<原始文件路径>

## 需求背景与范围

### 背景与痛点
（C-1 内容）

### 功能边界
（C-2 内容）

### 排除范围
（C-3 内容）

### 与现有功能的关系
（C-4 内容，若原文有）

## 功能说明

### 主流程
（C-5 内容）

### 异常与边界路径
（C-6 内容）

### 状态流转
（C-7 内容，若涉及）

## 技术指标与接口
（C-9 ~ C-13 相关内容，若涉及）

## 验收标准

### 正向 case
（C-14 内容）

### 异常 case
（C-15 内容）
```

---

## Phase 5 — 自我进化机制

评审过程中，若遇到以下情况，**必须暂停并用 AskUserQuestion 询问**：

1. PRD 中出现 completeness.md **未覆盖的新模式**
2. 某条现有规则与当前 PRD 的实际情况明显不匹配
3. 用户对某条评审结论表示「不适用」或「不需要检查」

**询问模板**：

> 我发现一个新模式：`[简短描述]`。是否将其添加到 references/completeness.md？

用户确认后，立即追加到 completeness.md 末尾，并注明 `<!-- updated: [日期] -->`。
